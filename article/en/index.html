Onboarding the Agent: AI in your repo, treated like a teammate

The agent is the new hire in every session: write its onboarding down in the repository, and review its work like anyone else's.

▶ Slides (pt-BR) Code · Nov 2026 · 8 min read

The first pull request

A pull request adds an endpoint to cancel an order. It builds. The tests pass. It still comes back from review with three comments.

  • DateTime.Now? Here we use TimeProvider, so tests can control the clock.
  • Validation throws an exception. Here invalid input returns ProblemDetails, the standard shape for HTTP errors.
  • The test is called Test1. The name doesn't say what it checks.

Nothing in that code is wrong in C#. It's wrong here, in this repository, by conventions nobody wrote down. Every developer has been that person once: the new hire on their first pull request.

This pull request was opened by an AI agent. The difference matters: a new hire learns after the second pull request. The agent starts from zero in every session.

An agent is a contributor that works in a loop

Autocomplete suggests the next line. Chat answers questions, and you copy and paste. An agent is a model that acts on the repository: it reads the code, runs commands, edits files, runs the build and the tests, and tries again when they fail.

That loop makes the agent a contributor: anyone who changes the project. It uses the same branch, the same pull request, the same checks and the same review as everyone else. The agent writes the code, but a person asked for it, a person reviews it, and a person answers for it in production.

The obvious fix for the first pull request is a better prompt every time. That's briefing the new hire out loud every morning: it works today, it's gone tomorrow, and each of us briefs differently. We don't onboard people that way. We write it down.

Instructions: the onboarding doc

Instructions are a file the agent loads at the start of every session: what's always true in this repository. In GitHub Copilot, the file is .github/copilot-instructions.md; other tools have their own names for the same idea.

A useful one has five parts, in this order: what the repository is, in one line; how to build and test, with the exact commands; the conventions; what not to do; and links to the docs that matter. Scoped instructions

Some rules only apply to some files. Scoped instructions live in .github/instructions/, and their applyTo field is a glob (a path pattern) that says which files they cover. The test rules only matter in tests, so the third review comment lives here:

Instructions guide; they don't enforce

Run the same request again, now with both files in the repository. The agent reads the instructions, uses TimeProvider and returns ProblemDetails. But the pull request arrives without a test.

The rule "every endpoint has a test" lives in the scoped file, and that file only loads when the agent touches tests/. The agent never opened a test file, so it never saw the rule. Scoped instructions apply to the files being edited. They don't tell the agent which files to create.

Is writing this more work than fixing the pull request? Once, yes; then every session and every new hire reuses it. And yes, the agent sometimes ignores instructions. Instructions guide. Formatters, analyzers and tests on the pull request enforce, and the human review catches the rest.

Skills: the how-tos, loaded when needed

Instructions say what's true. "Add an endpoint" is something else: a procedure. A skill is a procedure the agent loads only when the task needs it. It's a folder with a SKILL.md file: a short header, then the steps, in the order a teammate would follow them.

Step 5 is the missing test, now part of the job instead of a rule in a file the agent never opened.

The description decides whether a skill is used

At the start of a session, the agent only reads each skill's name and description. That's cheap. The body loads when a request matches the description.

So write the description like a search term. "Endpoint stuff" never matches anything. "Use when adding or changing an HTTP endpoint…" uses the words the request will use. SKILL.md is also an open standard, so the same file works in other tools.

With the skill in place, the same request loads add-endpoint, follows the steps, and the pull request comes with its test.

Custom agents: a different job

Instructions and skills shape how the agent works. Sometimes you want a different job altogether, like reviewing instead of writing. A custom agent is a role: its own instructions, often a narrower set of tools, picked for one kind of work. Which file does a rule go in?

If the rule is…it goes in
always true in this repositoryinstructions
true only for some filesscoped instructions

Try it: "tests follow Method_Scenario_Expected" is a scoped instruction. "How to add an endpoint's integration test" is a skill: the naming is a rule, but the steps are a procedure. "Review my pull request before I open it" is a custom agent.

A file the agent can't find doesn't exist

Each file loads at a different moment:

  • The session starts: the repository-wide instructions load.
  • The agent touches a file: scoped instructions whose applyTo matches are added.
  • A request comes in: skill descriptions are compared, and a match loads the skill.
  • You pick a custom agent. In VS Code and on GitHub, Copilot can also hand part of a task to one on its own, as a subagent (a helper agent started for a sub-task), unless the file sets disable-model-invocation: true. Visual Studio's docs only describe picking it yourself.

All of it depends on the files being exactly where the tool looks. In the sample repository, that's .github/: copilot-instructions.md, instructions/, skills/ and agents/. A file in the wrong folder doesn't cause an error. It's silently ignored.

AGENTS.md pays off with more than one tool

AGENTS.md is an open format, "a README for agents", read by many tools. In nested folders, the nearest file wins. The sample repository has a version of its instructions in this format.

It pays off when more than one tool works in the repository. With a single tool, its own file is enough, and moving later is a small change the agent itself can make. Either way, keep one source of truth: never the same rules in two files.

To help the agent find things: put each file exactly where the tool looks, write descriptions like search terms, link to docs instead of copying them, and keep the always-loaded file short. Everything in it costs context, what the agent can hold in mind at once, on every request.

Every repository, or one shared one?

Facts about this code live with the code. Things true for every repository, like a reviewer role or how the team writes pull requests, are candidates for sharing. There are two ways to share them, and each has a cost.

A shared repository, set up as user-level files

  • ✓ One place to improve
  • ✓ No copies drifting apart
  • ✘ Works only on machines where it's set up
  • ✘ Versioned apart from the code
  • ✘ Cloud agents and code review on GitHub don't see it

Files in each repository

  • ✓ Reviewed in the same pull request as the code
  • ✓ Work for anyone who clones
  • ✓ Work in the cloud too
  • ✘ Shared files get copied and drift

A middle ground: share generic roles and skills, keep anything that names this repository's code in the repository, and have each repository's instructions say which shared files exist.

The first pull request, again

Back to the endpoint from the start. The instructions bring TimeProvider and ProblemDetails. The skill brings the tests, named the right way. The reviewer checks the conventions before the pull request is opened. The human review is then about the change itself, not about our conventions. Almost always: instructions guide, and the checks and the review still catch the rest.

What you'd give a new hire on day one is what you give the agent:

  1. A short instructions file: build, test, conventions, don'ts.
  2. One skill for the task you repeat most.
  3. Scoped instructions only where a rule really differs.
  4. Every change it makes goes through a pull request and a human review.

Don't write it all upfront. Start with the build and test commands. When the same review comment shows up twice, it becomes a line. A rule nobody has needed yet is just more context to load.

The agent is the new hire in every session. Write its onboarding down in the repository, and review its work like anyone else's.
