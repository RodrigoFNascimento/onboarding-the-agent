Integrando o agente: IA no seu repositório, tratada como colega de time

O agente chega como pessoa nova no time em toda sessão: escreva a integração dele no repositório e revise o trabalho dele como o de qualquer outra pessoa.

▶ Slides Código · nov. de 2026 · 8 min de leitura

O primeiro pull request

Um pull request adiciona um endpoint para cancelar um pedido. Compila. Os testes passam. Mesmo assim, volta do review com três comentários.

  • DateTime.Now? Aqui usamos TimeProvider, para que os testes controlem o relógio.
  • A validação lança uma exceção. Aqui, entrada inválida retorna ProblemDetails, o formato padrão para erros HTTP.
  • O teste se chama Test1. O nome não diz o que ele verifica.

Nada nesse código está errado em C#. Está errado aqui, neste repositório, segundo convenções que ninguém escreveu. Todo desenvolvedor já foi essa pessoa um dia: a pessoa nova no time, abrindo o primeiro pull request.

Só que quem abriu esse pull request foi um agente de IA. E isso muda tudo: a pessoa nova aprende depois do segundo pull request. O agente começa do zero em toda sessão.

Um agente é um contribuidor que trabalha em loop

O autocomplete sugere a próxima linha. O chat responde perguntas, e você copia e cola. Um agente é um modelo que age sobre o repositório: lê o código, roda comandos, edita arquivos, roda o build e os testes, e tenta de novo quando algo falha.

Esse loop faz do agente um contribuidor: qualquer um que altera o projeto. Ele usa a mesma branch, o mesmo pull request, as mesmas verificações e o mesmo review que todo mundo. O agente escreve o código, mas uma pessoa pediu a mudança, uma pessoa revisa e uma pessoa responde por ela em produção.

A solução óbvia para o primeiro pull request é escrever um prompt melhor toda vez. É como explicar tudo de boca para a pessoa nova toda manhã: funciona hoje, some amanhã, e cada um explica de um jeito. Não é assim que integramos pessoas: colocamos tudo por escrito.

Instruções: o documento de integração

Instruções são um arquivo que o agente carrega no começo de toda sessão: o que é sempre verdade neste repositório. No GitHub Copilot, o arquivo é .github/copilot-instructions.md; outras ferramentas dão outros nomes para a mesma ideia.

Um arquivo útil tem cinco partes, nesta ordem: o que é o repositório, em uma linha; como fazer o build e rodar os testes, com os comandos exatos; as convenções; o que não fazer; e links para a documentação que importa. Estas são as convenções do repositório de exemplo: os dois primeiros comentários do review, agora por escrito, cada um com o seu motivo.

O que fica de fora importa tanto quanto. Se uma pessoa não leria no primeiro dia, o agente também não deveria ler. Deixe de fora o que o linter e o formatador já garantem, textos longos, segredos e tudo o que muda toda semana.

Instruções com escopo

Algumas regras só valem para alguns arquivos. As instruções com escopo ficam em .github/instructions/, e o campo applyTo delas é um glob (um padrão de caminho) que diz a quais arquivos elas se aplicam. As regras de teste só importam nos testes, então o terceiro comentário do review mora aqui:

Instruções orientam, não garantem

Repita o mesmo pedido, agora com os dois arquivos no repositório. O agente lê as instruções, usa TimeProvider e retorna ProblemDetails. Mas o pull request chega sem teste.

A regra "todo endpoint tem teste" está no arquivo com escopo, e esse arquivo só é carregado quando o agente mexe em tests/. O agente nunca abriu um arquivo de teste, então nunca viu a regra. Instruções com escopo valem para os arquivos que estão sendo editados. Elas não dizem ao agente quais arquivos criar.

Escrever tudo isso dá mais trabalho do que corrigir o pull request? Uma vez, sim; depois, toda sessão e toda pessoa nova reaproveitam. E sim, às vezes o agente ignora as instruções. Instruções orientam. Quem garante são os formatadores, os analisadores e os testes que rodam no pull request, e o review humano pega o resto.

Skills: o passo a passo, carregado quando precisa

Instruções dizem o que é verdade. "Adicionar um endpoint" é outra coisa: é um procedimento. Uma skill é um procedimento que o agente só carrega quando a tarefa pede. É uma pasta com um arquivo SKILL.md: um cabeçalho curto e, depois, os passos, na ordem em que uma pessoa do time os seguiria.

O passo 5 é o teste que faltava. Agora ele faz parte do trabalho, em vez de ser uma regra num arquivo que o agente nunca abriu.

A descrição decide se a skill é usada

No começo da sessão, o agente só lê o nome e a descrição de cada skill. Isso custa pouco. O corpo só é carregado quando um pedido combina com a descrição.

Por isso, escreva a descrição como um termo de busca. "Coisas de endpoint" nunca combina com nada. "Use when adding or changing an HTTP endpoint…" usa as mesmas palavras que o pedido vai usar. O SKILL.md também é um padrão aberto, então o mesmo arquivo funciona em outras ferramentas.

Com a skill no lugar, o mesmo pedido carrega a add-endpoint, segue os passos, e o pull request chega com o teste.

Agentes personalizados: outro trabalho

Instruções e skills mudam como o agente trabalha. Às vezes você quer outro trabalho, como revisar em vez de escrever. Um agente personalizado é um papel: tem as próprias instruções, muitas vezes um conjunto menor de ferramentas, e é escolhido para um tipo de trabalho. Este revisor confere uma mudança contra as convenções antes de o pull request ser aberto, e só consegue ler:

Abaixo do cabeçalho, o corpo lista o que verificar, como um checklist de review. Sem ferramentas de edição, ele não consegue "consertar" nada sozinho; a mudança continua sendo de quem a fez.

Teste você mesmo: "os testes seguem Method_Scenario_Expected" é uma instrução com escopo. "Como adicionar o teste de integração de um endpoint" é uma skill: o nome segue uma regra, mas os passos são um procedimento. "Revise meu pull request antes de eu abrir" é um agente personalizado.

Arquivo que o agente não acha não existe

Cada arquivo é carregado em um momento diferente:

  • A sessão começa: as instruções do repositório inteiro são carregadas.
  • O agente mexe em um arquivo: entram as instruções com escopo cujo applyTo combina.
  • Chega um pedido: as descrições das skills são comparadas, e a que combina é carregada.
  • Você escolhe um agente personalizado. No VS Code e no GitHub, o Copilot também pode passar parte de uma tarefa para um deles por conta própria, como subagente (um agente auxiliar iniciado para uma subtarefa), a menos que o arquivo defina disable-model-invocation: true. A documentação do Visual Studio só descreve a escolha feita por você.

Tudo isso depende de os arquivos estarem exatamente onde a ferramenta procura. No repositório de exemplo, isso é .github/: copilot-instructions.md, instructions/, skills/ e agents/. Um arquivo na pasta errada não dá erro. Ele é ignorado em silêncio.

O AGENTS.md compensa com mais de uma ferramenta

O AGENTS.md é um formato aberto, "um README para agentes", lido por várias ferramentas. Em pastas aninhadas, vale o arquivo mais próximo. O repositório de exemplo tem uma versão das suas instruções nesse formato.

Ele compensa quando mais de uma ferramenta trabalha no repositório. Com uma ferramenta só, o arquivo dela basta, e migrar depois é uma mudança pequena, que o próprio agente consegue fazer. Seja qual for a escolha, mantenha uma única fonte de verdade: nunca as mesmas regras em dois arquivos.

Para ajudar o agente a achar as coisas: coloque cada arquivo exatamente onde a ferramenta procura, escreva as descrições como termos de busca, coloque links para a documentação em vez de copiá-la e mantenha curto o arquivo que sempre é carregado. Tudo nele custa contexto, o quanto o agente consegue ter em mente de uma vez, em todo pedido.

Em cada repositório, ou em um compartilhado?

O que é sobre este código fica junto do código. O que vale para todo repositório, como um papel de revisor ou o jeito como o time escreve pull requests, é candidato a ser compartilhado. Há dois jeitos de compartilhar, e cada um tem seu custo.

Um repositório compartilhado, configurado como arquivos de usuário

  • ✓ Um lugar só para melhorar
  • ✓ Sem cópias divergindo
  • ✘ Só funciona nas máquinas onde foi configurado
  • ✘ Versionado longe do código
  • ✘ Agentes na nuvem e o review de código no GitHub não o enxergam

Arquivos em cada repositório

  • ✓ Revisados no mesmo pull request que o código
  • ✓ Funcionam para qualquer um que clona
  • ✓ Valem na nuvem também
  • ✘ Arquivos comuns são copiados e divergem

Um meio-termo: compartilhe papéis e skills genéricos, mantenha no repositório tudo o que cita o código dele, e faça as instruções de cada repositório dizerem quais arquivos compartilhados existem.

O primeiro pull request, de novo

De volta ao endpoint do começo. As instruções trazem o TimeProvider e o ProblemDetails. A skill traz os testes, com o nome certo. O revisor confere as convenções antes de o pull request ser aberto. Aí o review humano passa a ser sobre a mudança em si, não sobre as nossas convenções. Quase sempre: instruções orientam, e as verificações e o review continuam pegando o resto.

O que você daria para uma pessoa nova no primeiro dia é o que você dá ao agente:

  1. Um arquivo de instruções curto: build, testes, convenções, o que não fazer.
  2. Uma skill para a tarefa que você mais repete.
  3. Instruções com escopo só onde uma regra realmente muda.
  4. Toda mudança feita por ele passa por um pull request e por um review humano.

Não escreva tudo de uma vez. Comece pelos comandos de build e de teste. Quando o mesmo comentário aparecer duas vezes no review, ele vira uma linha. Uma regra de que ninguém precisou ainda é só mais contexto para carregar.
